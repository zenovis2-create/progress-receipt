## Body

"Finished. Everything works." is not the same as "here is what I changed and what I actually verified."

progress-receipt turns a bounded Git range into one shareable HTML receipt:

- a provenance-labeled change inventory — what changed, and where each fact came from
- four claim states kept separate: `changed` / `verified` / `blocked` / `not_observed`
- the commands that ran, and their real exit codes
- reviewed captures — screenshots an agent or human actually looked at
- explicit gaps — what nobody checked

The point is the evidence boundary, not a rubber stamp. A "verified" receipt can still carry a blocked claim: the report describes the evidence package, and a fresh, honestly-evidenced blocker stays visible.

Python 3.10+, standard-library only, no telemetry. The `demo` command runs the real collect → render → accept path against an isolated canned Git fixture, so there is no network and no private data.

Live receipt — generated by this repo's own pipeline and shipped with it:

## Likely comments and replies

### "Isn't this just CI plus a prettier diff?"

CI tells you whether configured jobs exited successfully. This also records a bounded Git inventory, provenance-labeled claims, explicit blockers and gaps, reviewed captures, and integrity hashes in one report — and still does not claim formal correctness.

### "How can a report be verified if one of its claims is blocked?"

Report status applies to the evidence package, not as an aggregate of claim statuses. `verified` means the presented evidence cleared the contract; a fresh, truthfully evidenced blocker can remain visible.

### "Are you claiming the report cannot leak secrets?"

No. Text sanitization targets documented patterns on a best-effort basis, and image pixels are not machine-sanitized; every published capture requires a recorded agent or human review.
